# M0: Board bring-up

Goal: a Vivado project, Linux running on the PS, something trivial blinking from
the PL, and a rebuild and reload loop whose cost is known.

M0 is complete when all five hold:

1. The board boots Linux from the SD card to a login prompt.
2. A PL-driven LED blinks, from a bitstream built locally rather than prebuilt.
3. `/proc/iomem` and `/proc/meminfo` from the running board are recorded below.
4. A clean rebuild and reload has been done twice, with the cost written down.
5. The project regenerates from `hw/scripts/` without the `.xpr`.

## Toolchain

Vivado and Vitis **2025.2**.

Verified by running Vivado in batch rather than by inspecting directories:

| Check | Result |
|---|---|
| Version | 2025.2 (SW build 6299465) |
| ZU3EG parts available | 51, including all eight `xczu3eg-sfvc784-*` grades |
| Package on this board | `sfvc784`, present |
| Board part resolves | `realdigital.org:aup-zu3-8gb:part0:1.0` |
| Board `PART_NAME` | `xczu3eg-sfvc784-2-e`, speed grade **-2** |

The speed grade is read off the board file, not assumed. Setting `board_part`
overrides `part`, so an assumed `-1` would have been silently corrected and then
quietly disagreed with every timing report afterwards.

## Board files: fetched, not vendored

Out of the box `board.repoPaths` is empty and no AUP-ZU3 board is visible, so a
project cannot pick up the DDR4, clock and MIO preset.

`hw/scripts/fetch_board_files.{sh,ps1}` pulls `board-files/aup-zu3-8gb` from
[RealDigitalOrg/aup-zu3-bsp](https://github.com/RealDigitalOrg/aup-zu3-bsp) into
`hw/board_files/`, which is gitignored. They are deliberately **not** committed:
upstream ships no LICENSE, so redistributing them from a public repo is not ours
to do. `hw/scripts/board_repo.tcl` points Vivado at that directory and defines
`BOARD_PART` and `FPGA_PART`. Nothing is written into the Vivado install tree, so
the dependency travels with the repository rather than with the machine.

The board ships in 4 GB and 8 GB variants which are not interchangeable. This
project targets the 8 GB variant.

## Design structure

**The block design holds the processing system and nothing else.** All custom
fabric logic lives in SystemVerilog under `hw/rtl/`, with `top.sv` instantiating
the generated BD wrapper alongside it.

That split was partly forced and partly chosen. Forced: Vivado's module-reference
flow rejects SystemVerilog as the top file of a referenced module, so `blink`
could not be dropped into the BD as a cell. Chosen: keeping the PL design as
readable source rather than as a diagram matters more as the traffic generator,
filter stage and DMA front end arrive.

Two deliberate PS settings:

- **PS-to-PL AXI masters disabled** (`M_AXI_HPM0_FPD`, `M_AXI_HPM1_FPD`,
  `M_AXI_HPM0_LPD`). The board preset turns them on, but with no PL logic behind
  them there is nothing to drive their clocks and nothing in their address
  spaces, and `validate_bd_design` fails on the unconnected clock pins. M2
  re-enables one to carry the DMA control interface, and adds the `S_AXI_HP` or
  `S_AXI_HPC` slave the DMA writes DDR4 through. That is also where the cache
  coherence decision gets made, since HP and HPC differ in whether writes are
  snooped against the PS caches.
- **`pl_clk0` enabled at 100 MHz.** This is the clock the blink divider is
  parameterised against, and it is the clock the free-running cycle counter will
  run on at M1. Every latency figure this project eventually reports is
  denominated in its cycles.

## PL heartbeat

`hw/rtl/blink.sv` divides `pl_clk0` down and drives a binary counter onto the
eight user LEDs. A counter rather than a single toggling LED, because it makes
the divider ratio observable: if the clock is not what you think it is, a counter
shows it immediately whereas a lone blink does not.

`hw/tb/blink_tb.sv` checks that reset holds the LEDs at zero, that the counter
advances exactly every `DIV` clocks rather than approximately, and that it wraps
cleanly.

The testbench earned its keep on the first run by failing. It reported the
counter advancing one clock early, every tick, consistently. The fault was in the
stimulus, not the design: releasing `rst_n` with a blocking assignment on the
same `posedge` the DUT samples is a race, and whether the release lands on that
edge or the next one depends on scheduler order. Reset is now released on the
falling edge. Worth keeping as a habit, since the same race would otherwise
reappear silently in every future testbench.

Pin locations in `hw/constraints/aup_zu3.xdc` come from the board file's
`part0_pins.xml`, not from the reference manual, so they stay consistent with
whatever the preset configures. All PL user IO on this board is `LVCMOS12`.

## Linux path: Buildroot, not PetaLinux

PetaLinux 2025.2 states these host requirements:

| Requirement | Stated |
|---|---|
| Supported hosts | Ubuntu 22.04.3 / 22.04.4 / 22.04.5 LTS, OpenSuse Leap 15.4, AlmaLinux 8.10 / 9.4 / 9.5 |
| Free disk | 100 GB |
| RAM | 8 GB |
| Cores | 8 minimum |

Ubuntu 24.04 is not on the 2025.2 list, and WSL is not listed as supported at
all. The development host for this project is a 4-core mobile part, where a Yocto
build runs into hours per iteration. That directly undermines M0's own acceptance
criterion, which is a rebuild loop that is not a fight.

PYNQ was considered and ruled out: the `Xilinx/AUP-ZU3` repo ships no prebuilt
image, only a `make image-8gb` target, and that requires PetaLinux **and** Vivado
2024.1. It costs more than PetaLinux, not less, and drags the whole project back
a release.

So Linux is built with **Buildroot** instead. Vitis generates the FSBL and PMU
firmware from the exported XSA and `bootgen` packages BOOT.BIN; Buildroot builds
ATF, U-Boot, the kernel and a minimal rootfs. It runs on the host as it stands,
needs a fraction of the disk, and rebuilds in minutes.

Linux itself is not optional, and it is worth being explicit about why, because
the whole project rests on it. M6 is an interrupt-per-packet, copy-through path
where userspace calls `read()`; bare metal has no kernel, no syscall and no
`copy_to_user`, so there would be nothing to bypass and nothing to compare
against. M4 verifies zero syscalls in the steady state with `strace`. M3 is a
device tree `reserved-memory` node. Remove Linux and the project's central claim
becomes untestable.

Anything reserved above 4 GB forces the PL DMA engine to 64-bit addressing, so
